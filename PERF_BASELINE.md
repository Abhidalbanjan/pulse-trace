# PulseTrace — Ingestion Performance Baseline

_ROAD_TO_100 · F0.2 — the R4 (scale & performance) evidence for the telemetry
ingestion hot path. Generated by the harness in [`scripts/load/`](scripts/load/);
the results block below is machine-written by `run-baseline.sh`, not by hand._

## Why this exists

Most pillar readiness scores were historically capped by "scale unproven." The
ingestion path — **gateway → log-service queue →
Kafka → Quickwit/ClickHouse** — is the first thing to fall over under real customer
traffic, and it is exercised by *five* different decoders (native, OTLP, and the
Datadog/Splunk "Trojan Horse" migration paths). A regression in any one of them is
invisible to the Go unit tests and the Playwright e2e flow. This harness closes
that gap: it drives every log-ingest protocol at a sustained arrival rate and
records both **gateway latency** and **downstream back-pressure**.

## What the harness measures

| Layer | Signal | Source |
| --- | --- | --- |
| Gateway HTTP | p50/p95/p99/max latency + failure rate, **per protocol** | k6 (`ingest-load.js`) |
| Kafka | consumer-group lag across all groups (does the log topic drain?) | `collect-infra-metrics.sh` |
| ClickHouse | active parts, concurrent merges, row count (insert/merge pressure) | `collect-infra-metrics.sh` |
| Containers | peak CPU % / mem MiB for gateway + log-service | `docker stats` |

## Protocols driven

All converge on the same downstream but exercise distinct gateway decoders:

| Protocol | Endpoint | Success | Path |
| --- | --- | :---: | --- |
| `logs` | `POST /api/v1/logs` | 201 | native JSON batch → Kafka |
| `otlp_logs` | `POST /v1/logs` | 200 | OTLP/HTTP JSON → sink → Kafka |
| `dd_logs` | `POST /api/v2/logs` | 200 | Datadog logs migration → Kafka |
| `splunk` | `POST /services/collector` | 200 | Splunk HEC migration → Kafka |
| `otlp_metrics` (opt-in) | `POST /v1/metrics` | 200 | OTLP/HTTP JSON → collector |

## Thresholds (fail the build on regression)

Baked into `ingest-load.js`, enforced by k6's exit code:

- **Per protocol:** `p95 < 800 ms`, `p99 < 1500 ms` — ingestion is a fire-and-forget
  enqueue and must stay fast even at peak.
- **Global:** HTTP failure rate `< 2%`, accepted-batch checks `> 98%`.

## Rate model (why the numbers are what they are)

The gateway's `telemetry-ingest` limiter caps `/api/v1/logs` + `/v1/logs` at
**100 req/s per tenant** (6000/60s; migration 007). `dd_logs` and `splunk` are on
separate paths outside that rule. `RATE` is the **aggregate** arrival rate, split
evenly across enabled protocols, so the default full profile
(`logs,otlp_logs,dd_logs,splunk` @ 120 req/s → 30/s each) keeps the two
rule-covered protocols at 60/s combined — deliberately under the 100/s ceiling, so
the run measures *ingestion latency at a permitted sustained rate*, not how fast the
limiter starts returning 429s. Finding the true throughput ceiling is a separate,
manual exercise (raise the limit or point at a dedicated tenant): see below.

## How to reproduce

```bash
docker compose up -d --build            # bring the stack up
scripts/load/run-baseline.sh            # waits for health, runs k6 + sampler, updates this file
# or a single protocol / custom rate:
PROTOCOLS=logs RATE=80 DURATION=30s scripts/load/run-baseline.sh
```

- **CI (per-PR, fast regression gate):** the `load-test` job runs `PROTOCOLS=logs`
  @ 80 req/s for 30s — a quick guard that the native path hasn't regressed.
- **CI (scheduled scale run):** the `scale-baseline` job runs the full multi-protocol
  profile for 2m and uploads the summary + this file as artifacts.

### Finding the throughput ceiling (manual)

The per-PR/scheduled runs sit *under* the limiter on purpose. To find the ceiling,
raise or disable the `telemetry-ingest` rule (admin → rate-limits, or a dedicated
tenant with a higher tier) and ramp `RATE` until either a threshold breaches or
Kafka lag grows without bound at end-of-run. Record that number in the results
block's ceiling note.
