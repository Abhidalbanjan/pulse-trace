## Why this file exists

[COMPETITIVE_OPENOBSERVE.md](docs/COMPETITIVE_OPENOBSERVE.md) makes claims about
storage cost and query performance. Every one of them was, until this harness
existed, either **their marketing** (the 140× and 2 PB/day figures) or **our
guess**. Neither belongs in an engineering plan that allocates six weeks to
closing a storage-economics gap.

This file is the scoreboard. It is expected to publish losses as prominently as
wins — a benchmark you only run until it agrees with you is not a measurement.

## Method, and what would invalidate it

- **Identical corpus, hash-verified.** Both targets ingest the same
  byte-reproducible corpus; `load.sh` refuses to run if its SHA-256 does not
  match. An input that drifts cannot distinguish a slower engine from a heavier
  dataset.
- **Native ingest and query paths on both sides.** Forcing either product onto
  the other's wire format would measure a translation layer.
- **Equal resource caps.** Recorded in the results block. An uncapped single
  binary against a capped 23-container stack is not a result.
- **Pinned OpenObserve image.** Recorded in the results block.
- **Warm-up discarded, errors counted.** The first call pays connection setup
  and cache population; failures are reported rather than dropped.

Read the numbers with the sample size in mind: nearest-rank percentiles over
`iterations` samples support less precision than three significant figures
would suggest.

## Status of the recorded run

⚠️ **The block below is a pipeline validation, not the benchmark.** It was
produced from an 8 MiB smoke corpus, where both systems hold everything in
memory and the timings are dominated by request overhead. Do not quote its
latencies.

Two things in it *are* meaningful, because they are structural rather than
size-dependent:

- **2 of 6 query classes are not expressible against PulseTrace at all** — the
  log API offers filters and a row limit, not `GROUP BY`. That is dimension D3
  measured rather than asserted.
- **The regex class fails outright.** Not slow — erroring. Quickwit 0.8 parses
  the `field:/…/` syntax `regexClause` emits as a *wildcard* query, so any
  pattern containing regex metacharacters returns a 502 and only a literal
  string works. The Log Explorer offers a regex toggle for a feature that
  cannot work. Tracked separately; it is the same family as the phrase-search
  defect (`record: basic`) already fixed.

A real run needs the 10 GiB corpus and both stacks under matched resource caps.

## How to reproduce

```bash
go run ./scripts/bench/corpus --size-mb 10240 --seed 42 --out corpus.ndjson
docker compose up -d
docker compose -f scripts/bench/compose.openobserve.yml up -d
EXPECT_SHA256=<hash> ./scripts/bench/load.sh --target pulsetrace  --corpus corpus.ndjson
EXPECT_SHA256=<hash> ./scripts/bench/load.sh --target openobserve --corpus corpus.ndjson
./scripts/bench/run-benchmark.sh --corpus corpus.ndjson --seed 42
```

### Capability gaps

2 of 6 query classes cannot be expressed against PulseTrace at all:

- **Full-scan aggregation** — PulseTrace has no aggregation API for logs. The log surface exposes filters and a row limit, not GROUP BY — a user cannot ask this question at all. This is dimension D3 (query power) measured rather than asserted, and it is what phase P3 exists to fix.
- **High-cardinality group-by** — Same ceiling as the full-scan aggregation: no GROUP BY, so a 50k-cardinality ranking is not expressible against the log API.

## Reading the capability gaps

Where a query class reports **not expressible** for PulseTrace, that is not a
missing measurement — it is the measurement. It means a user cannot ask that
question at all, which is dimension **D3 (query power)** in the competitive
analysis, and precisely what phase **P4** of the implementation plan exists to
fix. A latency comparison would understate that gap by making it look like a
number we simply did not collect.
